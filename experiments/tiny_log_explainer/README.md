# ESP32 离线日志解释实验

这个模型只用于 TF 日志页的“小模型解释这条日志”。输入一条已保存的 log，ESP 上的模型预测日志意图，网页按预测结果显示受控的中文说明与待核对事项。它是**有实际训练权重的文本分类模型＋说明模板**，不是自由生成文字的大语言模型，也没有学习或调用故障处置策略。

## 文件与复现

- `samples.json`：13 类、每类 10 个合成日志模板。必须逐条审核标签后再加入真实样本。
- `train.py`：Python 标准库训练稀疏 softmax 分类器，固定种子。v2 使用 2048 维 FNV 文本特征，包含词、相邻词以及下划线枚举的子词；不使用设备编号、时间和事件编号作为分类依据。
- `inference.h`：ESP 和桌面共用的 C++ 推理实现。v2 的 17 类参数约 136 KiB，只读放在固件中；输入限制 1024 字节，无网络服务依赖。
- `corpus/sources.json`：15 份官方资料的标题、适用系列、章节和原始网址。
- `corpus/build_corpus.py`、`corpus/h3c.json`：47 个事件/状态条目，对应 94 条独立编写的改写语料；包含文档来源，**并非从现场采集的日志**。
- `corpus/additional.json`：新增登录/AAA 失败、生成树保护、MAC 迁移、资源压力四类的合成模板。
- `qualify.py`：36 条另行编写的语义回归用例，检查高分结果是否出现 up/down、告警/恢复、保护/环路、失败/锁定混淆。
- `artifacts/`：训练权重 JSON、可编译权重头文件、分组数据、预测对照和完整指标。
- `verify.py`：检查模板组不跨分集、Python/C++ 得分一致、长输入/空输入拒答，并运行 ASan/UBSan。

在项目根目录执行：

```sh
.venv/bin/python experiments/tiny_log_explainer/corpus/build_corpus.py
.venv/bin/python experiments/tiny_log_explainer/train.py
.venv/bin/python experiments/tiny_log_explainer/verify.py
.venv/bin/python experiments/tiny_log_explainer/qualify.py
.venv/bin/python tools/embed_network_page.py
PLATFORMIO_CORE_DIR="$PWD/.pio-core" "$HOME/.platformio/penv/bin/pio" run -e esp32-s3-log-ai-lab
```

v1 每类模板整组按 6/2/2 划分训练/验证/测试，780/260/260 条，实际只有 78/26/26 个模板组。v2 加入 H3C 资料改写及协议适配后，按相同事件家族整组划分，连带的 up/down 和告警/恢复不跨分集；另外排除去掉编号后特征完全相同的跨集模板，修正 v1 仅凭模板名检查时漏掉的重复。

v1 的开发测试强制分类准确率约 69.6%，门槛 0.90 后回答 83/260 条（31.9%）。这些分集曾用于开发，**不是盲测，更不是实际交换机可靠性评估**。`baseline/` 保留原权重和原指标；v2 的 `metrics.json` 也会用相同的原 260 条测试文本对比两个模型，属于开发回归比较，不能视为独立泛化证明。匹配分没有校准为根因正确率。

## v2：H3C 资料扩充训练

合计 3240 条改写/合成样本：训练 2282 条（137 组）、验证 522 条（37 组）、测试 436 条（38 组）。同组变量扩充的日志高度相关，不能算作相同数量的独立现场事件。资料覆盖多个 Comware 产品系列；**不代表已经适配某一台 S5120 或现场固件版本**。所有文档为语义依据，未将完整手册当作模型语料打包。

v2 开发测试强制分类准确率约 83.9%，回答覆盖率约 49.1%；接受的 214 条合成样本全部匹配标签。36 条语义回归中强制分类约 88.9%，回答 26 条，其余拒答，未发现已接受的错误分类。H3C 单独留出的测试只有 4 个事件家族，详情见 `metrics.json`，规模仍很小。上述 100% 均不可外推到真实环境。

新增四类显示说明，把 `STP_LOOP_PROTECTION` 的缺少 BPDU、MAC 地址迁移与明确环路告警区分开，把 AAA/登录失败与账户锁定区分开；CPU/内存异常单独解释。回执成功、来源在线和厂商恢复报告不会成为模型验证处置成功的依据。

## 设备上使用

实验环境 `esp32-s3-log-ai-lab` 继承普通固件，仅启用 `ESP_LOG_AI_EXPERIMENT=1`，不启用 MQTT 实验。默认构建环境保持不变；网络和交换机配置的保存格式不变。

1. 双击 BOOT，看到青灯每轮闪两下。
2. 手机或电脑连接 `ESP-Logs-…`，打开设备查看页（常见地址 `http://192.168.4.1/`）。
3. 查看 TF 记录，点击某条蓝色解释区域的“小模型解释这条日志”。
4. 模型不确定时明确拒答，原有证据解释仍保留。强制分类的内部候选不会在拒答时当作结论展示。

`GET /model/explain?log=...` 仅在物理按键打开的十分钟窗口内可用；普通固件返回 503。输入不会被模型写入 TF/NVS，不会送往服务器，也不会输入 BDI。实验串口诊断 `H3C AI <log>\n` 同样绕过 BDI，仅输出 `[LOG-AI]` JSON，输入仍受既有 511 字节串口帧上限约束。串口诊断在实验固件中随 USB 可用，不依赖网页窗口。

低分、空内容、超长内容和未知类拒答。当前主要训练英文日志及枚举字段，中文自由文本、厂商新格式、缩写和未见事件可能无法解释，也可能误判。输入中如果缺少状态、混合多条日志或含有矛盾字段，现有分类器仍可能误判，不能依赖模型判断设备状态。页面保留“实验”提示。它不会把 ACK SUCCESS 当作恢复证据，不参与解锁、关端口、SSH、Telnet 或任何自动操作。

下一步需收集真实设备上经过人工确认的日志意图标签，并按设备、事故和采集批次划分独立评估集。不要把演示日志标成真实根因样本。

## 2026-10-31 实物实验结果

实验版已烧录到当前 ESP32-S3-ETH。7 组 USB 推理输出与训练端一致，另连续推理 40 次通过；测试输入都走 `H3C AI`，没有作为故障输入交给 BDI。串口请求往返约 5–9 ms，包含 USB 开销，并非纯推理耗时。原 USB 网关已恢复。

用户双击 BOOT 后，通过实际 ESP 热点验证了内嵌页面包含模型按钮、5 组 HTTP 推理及连续 20 次 HTTP 推理。锁定、断链、回执样例按预期显示候选；低分温度样例与未知内容按预期拒答。空输入/超过 1024 字节输入返回 400，查看模式配置读取返回 403。推理后实际 TF 文件仍可读，卡状态 ready，未保存计数 0。电脑已恢复原 Wi-Fi。

本机证据在 `test/.runtime/tiny-log-hardware.json` 和 `test/.runtime/tiny-log-http.json`（运行数据，不提交源码）。前端 76 项测试、网页构建、普通/模型实验固件构建、31 项 Python/C++ 对照和 ASan/UBSan 均通过。这验证了部署与接口链路，不代表完成真实交换机故障解释准确率验收。

## v2 实物更新与复核

2026-10-31 已将 `tiny-log-v2-h3c` 烧录到同一块 ESP32-S3-ETH。54 组 USB 推理（包含 36 条语义回归）与 Python 对照通过，连续 40 次推理通过。实际热点上的 13 组 HTTP 推理及连续 20 次调用通过，回应的模型版本为 v2；STP 保护、MAC 迁移、AAA 失败、CPU 告警等新类已在设备上返回正确标签。空输入和超长输入被拒绝，查看模式仍禁止读取配置，推理后 TF 文件可读取。

前端 77 项测试、网页构建、普通/实验固件构建、49 项 Python/C++ 对照及 ASan/UBSan 通过。实验固件 Flash 占约 63.9%，静态 RAM 约 20.2%。原 USB 网关和电脑原 Wi-Fi 已恢复。

注意：本次开机在网页检查前已经存在未保存记录，第一次查看累计 7 条，后续复核开始时累计 8 条；后续这轮 HTTP 测试前后均为 8，期间未增加。卡状态保持 ready，但不能声称日志零缺口，既有丢弃原因未在本次模型训练任务中确定。最新运行证据仍写入上述两个本机 JSON，历史 v1 的文字记录不代表当前计数。
