# TF 卡故障记录

ESP32-S3-ETH 板载 TF 卡槽通过第二个 SPI 主机使用，GPIO 为 CS=4、MISO=5、MOSI=6、SCK=7。W5500 仍使用原有 SPI 和 9–14 引脚，不共用总线。依据 [Waveshare Arduino TF 卡例程](https://docs.waveshare.com/ESP32-S3-ETH/Development-Environment-Setup-Arduino#03_sd_card)。

插入已准备好的 FAT32 TF 卡再启动。固件不格式化卡，不支持此流程下的 exFAT/NTFS，也不会修改卡上的其他目录。已存在的 `esp-journal` 目录必须带本程序的 `format.txt` 标记，否则拒绝写入，避免覆盖其他文件。

## 保存内容

卡上 `esp-journal` 目录包含三类 UTF-8 JSONL 文件（每条非空行为一条 JSON）：

| 文件 | 内容 |
|---|---|
| `00000000000000000003-summary.jsonl` | 故障摘要、来源失联/恢复、ESP 网口链路变化、处置证据和记录缺口 |
| `00000000000000000001-raw.jsonl` | 已接受的 `H3C LOG` 输入和 `[BDI]` 输出，标注方向 |
| `00000000000000000002-process.jsonl` | `[BDI][CMD]`、`[BDI][ACK]`、`[BDI][RECOVERED]` 处置过程 |

摘要包含设备、组件/端口、故障类型、事件 ID、上报原因、严重程度、开始时刻和已确认恢复时的持续时长。处置记录保留请求 ID、重试次数和结果。原始日志中常见的密码、令牌等字段会脱敏；配置接口、BLE 配置数据和 MQTT 密码不接入此记录器。

文件名前 20 位是递增创建序号，跨三类记录排序；重新挂载从现有最大序号继续，不依赖是否校准时间。文件中可以包含多个开机周期。

每条正常记录包含 `boot_id`、本次开机 `uptime_ms` 和 `unix_ms`。系统未取得可信时间时 `unix_ms=null`，不编造日期。跨开机周期用 `boot_id` 区分，前一周期未完成的事件不自动判为恢复；网关重放的故障会在新周期重新跟踪。

这是依据确定规则生成的证据摘要，不在 ESP 上运行大模型：

- `reported_cause` 仅表示日志来源声称的原因，不代表独立确认的根因。
- 来源心跳过期只记 `SOURCE_LOST`，不能仅据此认定交换机断电或环路。
- 网口 link down 不等于整台交换机宕机；恢复通信不等于故障恢复。
- 命令成功 ACK 仅记为过程证据；只有权威状态模型在收到恢复信息并完成稳定性验证后清除故障，摘要才写 `RECOVERED`。
- 当前数据入口仍是 USB 网关，可能是模拟数据；启动摘要明确写出这一点。此功能不会新增 SSH/Telnet 采集、环路隔离或自动网络补传。

## 断网、卡异常与容量

记录不依赖 MQTT 连接。独立写卡任务与 W5500 使用不同 SPI 主机；BDI/USB 主循环通过有界队列提交，不等待 SD 读写。卡未插入、无法挂载或写入失败时，每 30 秒重试，主循环继续工作。

- 队列最多 12 条，每条最多 2048 字节。长 BDI 输出会明确标注截断；仍超过队列单条上限或队列已满时计入 `dropped`。
- 失败或无卡期间只有有限 RAM 缓存，不能承诺全部保留。恢复写入后用 `RECORD_GAP` 明确记录未保存计数。
- 单个文件最多 512 KiB，记录内容合计最多约 12 MiB、最多 32 个文件。达到上限，或 TF 卡可用空间接近 1 MiB 时，按文件创建序号从小到大清理，随后继续写入。检查时留出额外 FAT 簇分配余量，所以可能稍早触发。
- 清理只涉及带本程序目录标记、且严格匹配 `20位十进制序号-raw/process/summary.jsonl` 的文件。文件创建后持续追加，淘汰单位是完整文件，不是单条记录；清理计数 `evicted` 按本次开机统计。非本程序文件不会被删除；若其他内容占满卡，且清理完自有文件仍无法留出空间，将显示写入失败并计入丢弃数。
- 旧版软件使用的 `raw-0.jsonl` 等命名不属于新版循环清理模式；如手动放入此类旧文件，不会被自动删除。
- 摘要最多同时跟踪 64 个活动故障，容量满时记录 `SUMMARY_CAPACITY` 并置 `summary_incomplete=1`。原始记录仍继续尝试写入。
- 每条写入后 flush/close。突然掉电、损坏或热拔卡仍可能丢失或损坏最后一条；重新挂载时会分隔残留尾部，离线读取工具应忽略空行并报告不完整 JSON。
- 拔卡读取前应停止设备写入并断电。TF 卡能保存已有证据，不能让已断电的交换机继续产生新日志，也不能替代独立供电和管理通道。

## 独立查看网页

无需重新配置网络，也无需改 bootloader：

1. 上电运行后，连续短按 BOOT 两次（每次约 0.1–0.5 秒，两次间隔不超过 0.6 秒）。青灯每轮闪两下表示已进入查看模式。
2. 手机/电脑连接 `ESP-Logs-<设备标识>` 免密码热点，选择继续连接。如果系统未自动弹出，浏览器打开 `http://esp.setup` 或串口日志显示的热点地址（通常 `http://192.168.4.1`）。自动弹窗由手机系统决定，不能保证所有手机自动打开。
3. 首页直接显示 TF 记录，不显示配置表单。切换“故障摘要 / 原始日志 / 处置过程”，选文件、看文件末尾或翻阅更早内容。默认显示所选类型最新创建文件的末尾。完整字段可展开查看，日志内容按文本渲染。
4. 点“关闭查看入口”立即关闭；否则开启十分钟后自动隐藏热点与 HTTP。双击 BOOT 可再次打开。读取不重写 NVS、不更改 IP/SSH/MQTT、不广播蓝牙配置服务。查看模式下配置读写接口返回 403。

已接网口的电脑也可在双击后打开 `http://<已配置的网口IP>/`，不需要换 IP。网口链路或交换机故障时使用设备自身的热点。热点是本地免密码入口，只在现场需要查看时打开。

长按 BOOT 三秒仍开启原有配置模式（蓝灯提示）。配置页面“TF 卡故障记录”中的“查看 TF 卡记录”链接也可打开 `/journal`，无需点击保存；这个链接不会改变当前配置模式。参数仍只有原来的一个“保存全部配置”按钮。

`GET /storage` 提供状态、成功写入数、未保存数、摘要容量与清理数，不回传密码。`GET /storage/files` 返回有界文件列表与空间快照；`GET /storage/read?file=...&offset=...` 提交最多 3072 字节的读取请求，随后用返回的 `job` 轮询。读取只接受记录文件名，不允许路径、任意卡文件或整卡下载。所有 SD 读写均在写卡任务内串行执行，网页只交换有界快照，不在 USB/BDI 主循环读卡。文件可能在翻阅前已被循环清理，此时刷新列表重新选择。

## 离线故障助手

TF 查看页内置离线规则解释器，在手机或电脑浏览器本地运行，不需要服务器、API 密钥或外网，也不在 ESP 上加载语言模型。解释与页面一起放在固件中，不加载外部脚本。每条完整记录下方自动显示故障现象和处置进展，展开后可查看可能原因（待核对）、排查建议、日志依据和解释范围；也可以关闭显示。

首版支持账户锁定、端口链路中断 / 管理关闭、温度、明确的环路类事件、电源与风扇告警，以及来源失联、链路变化、记录缺口等记录。它只提供解释与检查建议，不执行命令，也不把新增解释写回 TF 卡。原始证据继续保留，未知事件明确提示规则不支持。

每次仅分析当前读入的文件片段。命令与 ACK 需要匹配同一开机标识、请求、设备、组件及动作；恢复还要求同一事件、故障类型与先后时间，缺少标识或有歧义就不关联。`COMMAND_ACCEPTED` 和 `SUCCESS` 回执均不能单独证明故障恢复；来源恢复输入、心跳和在线也不能替代模型恢复记录。历史已验证恢复只说明记录当时的模型状态，不能当作实时正常；片段外的证据不作推测。

解释规则和测试分别在 `frontend/src/fault-explainer.js` 与 `frontend/test/fault-explainer.test.js`。编辑后运行 `python3 tools/embed_network_page.py`，将规则与页面共同嵌入 `src/journal_page.h`。Vite 构建仍使用同一模块源码。

## 验收

卡未插入时网页明确显示未检测到 FAT32 卡，不生成模拟 TF 记录；状态读取失败也不阻止原有配置保存。

实物验收需确认：插卡后 `sd_state=ready`；无卡时 BDI 仍工作；产生测试故障、回执、恢复和来源超时后断电取卡，核对三类文件；检查断网记录、轮转、异常拔卡与重新插卡。当前真实交换机采集未接入，因此模拟测试记录不能作为真实环路处置成功的证据。

原生按键、文件轮转策略与摘要测试分别位于 `test/boot_gesture.cpp`、`test/journal_files.cpp`、`test/fault_journal.cpp`；网页行为测试位于 `frontend/test/journal-page.test.js`。

原生摘要测试：`c++ -std=c++11 test/fault_journal.cpp -o /tmp/esp-fault-journal-test && /tmp/esp-fault-journal-test`。

## 2026-10-31 实物验证

在 ESP32-S3-ETH 板载槽插入 15.6 GB FAT32 TF 卡，普通固件已烧录。双击 BOOT 后青灯双闪，热点 ESP-Logs-f4697090 与只读首页开启；实际三类 JSONL 文件均已写入，并通过设备 HTTP 接口读回、UTF-8 解码和 JSON 解析。三类首段读取加 12 次连续复读通过，测试期间无重启，丢弃计数保持 0；配置 GET 接口和网络配置 POST 在查看模式下返回 403，路径穿越文件名被拒绝。电脑原 Wi-Fi 已恢复。验证摘要保存在本机 `test/.runtime/tf-card-validation.json`（运行数据，不纳入源码）。

首次实机读回发现，构造较大 base64 JSON 响应时，多个堆字符串副本会触发内存分配失败并重启。现改为固定缓冲区直接编码，每段上限 3072 字节，预留响应缓存；增加最大长度、编码填充和缓冲区边界回归测试，修复后重新烧录并完成上述实测。

这些记录来自现有 USB 模拟网关，验证的是 TF 保存与读取链路，不能作为真实交换机故障处置成功的证据。本次未填满 TF 卡，也未主动删除已有记录；近满清理仍需后续专门实物验收。
